# BBAI64 VXE384MP2 H.264 encoder feasibility assessment

[한국어](preanalysis-ko.md) · [D435i board validation](../d435i-rgb/preflight-en.md)

## Recommendation

Start with a **VXE external module port to r47 and a single encoder node in the BBAI64 Device Tree**. Retain Debian 13.6 and the existing `6.18.39-arm64-k3-r47-tidl3` baseline. Consider kernel changes only if the driver requires an API that cannot be accommodated in the external module. This assessment used static inspection. Builds, deployment, and pipeline tests remain follow-up work.

The user's D435i test captured 1080p30 YUYV, sustained 30 fps with software scaling and JPEG encoding, and streamed over TCP through SSH ProxyJump. The receiver exhibited severe interruption, and the tested camera configuration did not offer direct MJPEG. Quantify the CPU and transport benefits of H.264 with a follow-up comparison.

## Evidence and porting scope

- **Driver — port required.** The local PSDK Linux 11.02.00.04 image, `tisdk-adas-image-j721e-evm.tar.xz`, ships `updates/vxe-enc.ko` and `vxd-dec.ko`. Its opkg metadata names `ti-vxe-vxd-driver` version `6.12-r0.845` and recipe `ti-vxe-vxd-driver_6.12.bb`. The package pulls in both modules and `ti-multimedia-udev`. The encoder module itself declares no decoder dependency. Its vermagic targets TI 6.12.57, so it must be rebuilt against the r47 ABI. The r47 tree and config have no dedicated VXE driver or option. The exact driver **SRCREV and downstream patch list remain unverified**. Use the release manifest to identify the Yocto layer revision and applied bbappends, then capture `SRC_URI`, `SRCREV` and patches. [TI release notes](https://software-dl.ti.com/jacinto7/esd/processor-sdk-linux-jacinto7/11_02_00_04/exports/docs/devices/J7_Family/linux/Release_Specific_Release_Notes.html) · [TI recipe history](https://git.enea.com/cgit/linux/meta-ti.git/log/?h=scarthgap-next&id=a49d78970f36ad28d3c18b77288d870864e44797&showmsg=1)
- **r47 dependencies — partially verified.** The module declares `v4l2-mem2mem,videobuf2-v4l2,videodev,videobuf2-dma-sg,videobuf2-common`. The current config enables V4L2 mem2mem, VB2 V4L2 and DMA-SG as modules and enables DMA CMA. A static comparison found 115 of the TI module's 119 undefined symbols in r47's existing `Module.symvers`. The four absent names are `__mutex_init`, `init_timer_key`, `mutex_is_locked` and `sg_next`. These are source-porting investigation points. Target headers may inline an operation or emit different symbols. Review platform callbacks, V4L2/vb2, DMA and runtime PM against the exact target, then require successful modpost using its config, generated headers, symbols and toolchain. If kernel changes are necessary, build under a separate release name.
- **Device Tree — change required.** Both SDK SK and common-proc-board DTBs define `video-encoder@4200000`, compatible `img,vxe384`, a `0x100000` MMIO window, GIC SPI 181 level-high and exclusive power domain 153. Neither node has its own `clocks` or `memory-region` property. The local BBAI64 TIDL candidate DTB has no encoder node and exposes `k3_pds`. Add the node on the main bus using the BBAI64 provider reference. Verify the merge preserves existing reserved memory, remoteproc, RPMsg and DMA-heap properties. Verify the device DMA mask and SG/MMU addressing from driver source.
- **Firmware — encoder-specific provenance remains open.** The module has `topaz_upload_firmware` and declares no external firmware in `.modinfo`. It imports no firmware request helper directly. This suggests an embedded or otherwise locally supplied payload. Confirm its source and redistribution terms from the release source. The image's `vxd-dec-fw` package supplies `pvdec_full_bin.fw` for the decoder. No module or package evidence calls for replacing MCU2_0 or C71x firmware. Keep the existing noeth and DSP images.
- **GStreamer — verify discovery.** Check the device for mem2mem, NV12 on OUTPUT, H.264 on CAPTURE and permissions for the streaming account. Then check registration with `gst-inspect-1.0 v4l2h264enc`. If a usable node exists and the element remains absent, compare Debian plugin probing and caps with the TI release's GStreamer patches. Start with a copied NV12 input and verify stride, alignment, negotiated size and crop at 1080p. Evaluate DMA-BUF and hardware scaling after the basic path works. [TI codec formats and GStreamer examples](https://software-dl.ti.com/jacinto7/esd/processor-sdk-linux-jacinto7/11_02_00_04/exports/docs/linux/Foundational_Components_Multimedia_D5520_VXE384.html)

## Test gates and recovery

1. **Before deployment.** Preserve source revisions and SHA256 hashes of the candidate module, DTB and config. Check vermagic, symbols and Device Tree differences. The user builds and deploys the candidate through a separate boot entry while preserving the original tidl3 entry and firmware links.
2. **Encoder only.** Run `v4l2-ctl --list-devices` and check the encoder with `--all`, `--list-formats-out` and `--list-formats`. Encode 300 frames with `videotestsrc → video/x-raw,format=NV12,width=1280,height=720,framerate=30/1 → v4l2h264enc → h264parse → filesink`. Decode the result on the host and verify 300 frames at 720p. Require no encoder timeout or DMA error and a passing repeat run of the existing TIDL model in the same boot.
3. **Camera and transport.** Test D435i YUYV through software NV12 conversion and scaling to a local H.264 file. Count and discard invalid V4L2 input buffers, including short error buffers like the one in the previous RGB test. Then compare JPEG and H.264 at matching output size and frame rate over the same TCP/SSH ProxyJump route. Record sender CPU, transmitted bytes, received FPS and frame loss. Keep local encode and remote receive results separate.
4. **Stop and recover.** Stop at a probe failure, timeout, DMA error, changed TIDL memory layout or inference regression. Boot the preserved tidl3 entry and repeat the D435i RGB and TIDL checks.
