# BBAI64 camera and display feasibility assessment

2026-11-25 · [한국어](report-ko.md) · [Board inventory](board-inventory.txt) · [Work log](../worklog-en.md) · [Outcomes](../outcomes-en.md)

## 1. Decision and baseline

Start with D435i RGB over UVC. Linux has registered the Mini DisplayPort connector. Resolve MCU2_0 display ownership and confirm the MHDP firmware path before validating output. IMX219 needs a BBAI64-specific CSI overlay and a change in CSI ownership. The existing SDK exposes a candidate C API path for VPAC hardware ISP. Defer Edge AI middleware unless the application needs its plugins or demos.

Read-only SSH confirmed Debian 13.6, kernel `6.18.39-arm64-k3-r47-tidl3`, and boot marker `tidl-kernel-test-3`. The existing Python ONNX Runtime 1.15.0/TIDL EP baseline comes from the [prior validation results](../../bbai64-porting/python-ort-validation/results-en.md). The release baseline is J721E PSDK RTOS 11.02.00.06, Linux 11.02.00.04 and TIDL Tools 11_02_04_00. This assessment used inventory and static inspection. Device streaming, graph execution and builds are follow-up work. ## 2. Linux capture and display

- **CSI.** The live config and installed module files confirm `VIDEO_TI_J721E_CSI2RX=m`, `VIDEO_CADENCE_CSI2RX=m`, `PHY_CADENCE_DPHY_RX=m`, and `VIDEO_IMX219=m`. Live DT disables shims `4500000/4510000` and D-PHYs `4580000/4590000`. The staged candidate DTB agrees and models the Cadence receiver under the TI shim with a D-PHY reference. There is no current evidence that RAW capture requires a kernel patch. Source evidence is under `bbai64-porting/kernel-work/linux/drivers/media/platform/ti/j721e-csi2rx/` and `arch/arm64/boot/dts/ti/k3-j721e-beagleboneai64.dts`.
- **Overlay.** The installed and local `k3-j721e-sk-csi2-dual-imx219` targets the SK board and references its `csi_mux`, `cam0_i2c` and `cam1_i2c`. BeagleBoard's official 5.10 CSI1 overlay provides BBAI64 evidence for `main_i2c1`, address `0x10`, a 24 MHz clock, GPIO0_107 and two lanes. A ready-to-use r47 overlay and the historical CSI0 source were not verified. Start with CSI1. Check sensor power, reset, pinctrl, reciprocal endpoints and D-PHY against the r47 binding and driver. For a 15-pin module, verify the cable and pinout for the board's 22-pin connector. In the follow-up, apply the camera-only candidate offline and compare reserved memory, remoteproc `memory-region`, DMA heaps and existing active peripherals before boot testing. [BeagleBoard CSI1 source](https://github.com/beagleboard/BeagleBoard-DeviceTrees/blob/v5.10.x-ti-unified/src/arm64/overlays/BBAI64-CSI1-imx219.dts) · [Camera documentation](https://docs.beagleboard.org/accessories/cameras.html)
- **MiniDP.** The live chain is `4a00000.dss → a000000.dp-bridge → DP-1`, with `tidss` and `cdns-mhdp8546` bound. The SAPB diagnostic explicitly identifies unavailable HDCP. The driver defines `FW_NAME` as `cadence/mhdp8546.bin` in `cdns-mhdp8546-core.h`. The queried firmware directory did not contain a matching file. The local tidl3 build lists this file in `CONFIG_EXTRA_FIRMWARE`, so the built-in copy is the likely loading path. Confirm the running image configuration and the firmware request outcome separately. Basic test-pattern scanout can use CPU buffers and KMS. GPU-accelerated composition and the existing Vision Apps library have their own EGL/GLES/GBM dependencies. [Linux DRM/KMS](https://docs.kernel.org/gpu/drm-kms.html)
- **D435i.** Identify the RGB interface and its formats through V4L2. Evaluate depth formats, metadata and timestamps separately from accelerometer, gyroscope and video synchronization. librealsense native uses V4L2/UVC and HID/IIO. RSUSB uses libusb with appropriate device permissions. Pin a camera-firmware and SDK pairing before comparing backends. Consider a targeted driver patch only after documenting the failed required stream. The vendor DKMS matrix does not establish support for r47. [D435i IMU](https://github.com/realsenseai/librealsense/blob/master/doc/d435i.md) · [Linux backends](https://github.com/realsenseai/librealsense/blob/master/doc/installation_jetson.md)

## 3. Firmware ownership and TIOVX

Live `5c00000.r5f` is running. The on-disk `j7-main-r5f0_0-fw` SHA256, `567e257b39a2a6082c8a2394a3e49dea33b5add790449accae6d225f6bb5d695`, matches the [noeth artifact](../../bbai64-porting/firmware-work/deployment-noeth-en.md). The hash identifies the file inspected after boot. MCU2_1, both C66x cores and C71x also report running.

| Resource | Source and link evidence | Proposed owner |
|---|---|---|
| CSI2RX and capture | `BUILD_MCU_BOARD_DEPENDENCIES=yes` enables `ENABLE_CSI2RX`, `appCsi2RxInit` and `tivxRegisterVideoIOTargetCaptureKernels` | Linux V4L2/I²C |
| DSS | Same flag enables `ENABLE_DSS_SINGLE` and `ENABLE_DSS_EDP`, `appDssDefaultInit`, and Display/Display M2M target registration | Linux TIDSS/MHDP |
| VPAC | Independent `ENABLE_VHWA_VPAC` enables `appVhwaVpacInit` and MCU2_0 VISS/MSC/LDC/NF/FC and AEWB registration | MCU2_0 |
| DMPAC and DSP | J721E `app_init.c` has DMPAC SDE/DOF, C66x OpenVX/ImgProc, and C71x TIDL/TVM/ImgProc registration paths | MCU2_1 and the respective DSPs |

Evidence comes from SDK `vision_apps/platform/j721e/rtos/common/{app_cfg_mcu2_0.h,app_init.c}`, the noeth ELF/map and `firmware-work/build.sh`. `BUILD_ENABLE_ETHFW=no` leaves the independent board-peripheral setting in place. Linux DP binding does not establish exclusive DSS control. Evaluate a separate MCU2_0 candidate with `BUILD_MCU_BOARD_DEPENDENCIES=no`. Confirm removal of CSI2RX/TX, DSS, board and I²C initialization and preservation of FVID2, VPAC and IPC. Check ELF/map, resource table, SHA256 and memory ranges offline before user deployment. Confirm that TIDL still passes. Static code establishes initialization paths. Live register ownership was not measured.

The board's user staging contains `libtivision_apps.so.11.2.0`. The local corresponding ELF exports `tivxHwaLoadKernels`, `tivxVpacVissNode`, `tivxVpacMscScaleNode`, `tivxVpacLdcNode`, `tivxAewbNode`, `vxColorConvertNode`, `tivxCreateRawImage`, `tivxReferenceImportHandle/ExportHandle` and `tivxMemTranslateFd/VirtAddr`. The staged header set focuses on ONNX Runtime. A C graph needs headers from matching SDK TIOVX, Imaging and applicable Vision Apps APIs. ELF dependencies include EGL, GLESv2, GBM, `libti_rpmsg_char.so.0` and system libraries. The exports establish API candidates. Full Vision Apps coverage, target matching and graph execution remain to be tested.

VISS handles Bayer-to-YUV on MCU2_0 VPAC. The SDK's `tiovx/kernels/openvx-core/c66x/vx_color_convert_target.c` implements the DSP OpenVX color conversion target. Obtain RGB from NV12 with a supported DSP format combination or a CPU conversion. LDC needs lens-specific correction data or a mesh. CSI supports `VB2_MMAP | VB2_DMABUF`. Start with a copy path. Move to shared buffers after checking plane size, offset, pitch, alignment, address limits, cache synchronization, FD and queue lifetime, and heap access.

## 4. Minimum IMX219 ISP and DCC requirements

- The SDK image `tisdk-adas-image-j721e-evm.tar.xz` contains `/opt/imaging/imx219/linear/dcc_viss*.bin` and `dcc_2a*.bin`. Both families have generic, `_10b`, and resolution-specific variants at 320×240, 640×480, 1280×720, 1640×1232 and 1920×1080. The SDK also contains `imaging/sensor_drv/include/dcc_{viss,2a}_imx219.h` and `imaging/tools/default_DCC_profile_gen/configs/imx219_properties.txt`. Equivalence of the header arrays and individual image files was not established.
- Match the VISS/2A pair to the actual sensor mode, media-bus code and capture fourcc. Check Bayer order after flips, RAW8 versus RAW10, packed versus 16-bit RAW10 storage, stride and output dimensions. The SDK's 1920×1080 example is a reference mode. A NoIR-specific DCC profile remains unverified. Start with the standard profile for a smoke test and assess color, white balance and exposure under the intended visible and IR lighting before deciding on retuning.
- Populate `tivxCreateRawImage` from captured RAW. Supply VISS configuration and the ISP DCC bytes through `vxCreateUserDataObject` to `tivxVpacVissNode`. First run a stored RAW frame through VISS to NV12 using fixed exposure and gain. Then feed the VISS H3A statistics and 2A DCC into `tivxAewbNode`, returning exposure and gain to the Linux sensor subdevice. Adapt the RTOS sensor-control leg in the SDK example to Linux ownership. The Imaging implementation and API contract are required. Determine whether any separate Imaging library is needed from ABI and graph checks against the current exports. See `vision_apps/apps/basic_demos/app_single_cam/app_single_cam_common.c` for the VISS and AEWB graph. [TI VPAC ISP tuning](https://www.ti.com/lit/an/spracu7a/spracu7a.pdf)

## 5. Middleware and acceptance gates

The board has Debian GStreamer 1.26 packages and V4L2, app and KMS plugin files. No TI GStreamer plugin, TIOVX Modules or Edge AI Gst Apps installation was found in the search. Only `v4l2-ctl` appeared in the command lookup. Use standard V4L2/GStreamer, Python ORT and Linux DRM/KMS for RGB and display, and a direct C TIOVX graph for CSI ISP. TI wrappers become relevant for elements such as `tiovxisp`, existing YAML demos, or their memory pool and caps negotiation. For a later port, pin the exact repository revisions from the PSDK Linux 11.02.00.04 Yocto recipes/manifest. A Debian-compatible revision set remains unverified. Check CMake and SDK headers/Vision Apps ABI for Modules. Check Meson, GStreamer development packages, Modules, Apps Utils and required DL libraries for Plugins. Check Python, plugin and configuration dependencies for Apps. Verify Debian pkg-config, GStreamer/GLib and dynamic-library resolution in an isolated prefix. [TI Modules](https://github.com/TexasInstruments/edgeai-tiovx-modules) · [TI Plugins](https://github.com/TexasInstruments/edgeai-gst-plugins) · [TI Apps](https://github.com/TexasInstruments/edgeai-gst-apps)

1. **Baseline and RGB.** Record existing model results and firmware hashes. Use `lsusb -t`, `v4l2-ctl --list-devices` and `--list-formats-ext` to find the color node. Capture 300 frames at one mode and verify increasing timestamps, expected frame size and error-free capture. If required, test depth, RGB and IMU together in librealsense.
2. **Ownership and DP.** Check the MCU2_0 candidate offline and retain the noeth recovery path. With a monitor attached, inspect `/sys/class/drm/card0-DP-1/{status,modes,edid}` and `modetest -M tidss -c`. Require the intended mode and stable test-pattern output. Distinguish DRM master and device permission failures from link failures.
3. **CSI and ISP.** Test one camera overlay in a separate boot entry. Require sensor-to-Cadence-to-TI capture links in `media-ctl -p`, consistent pad and capture formats, and sustained RAW capture. Follow with stored RAW-to-NV12, live VISS, and then AE/AWB. Record Bayer/stride errors, color bias and unstable exposure independently.
4. **Integration.** Move from one to multiple models while observing dropped frames, latency, CMA and heap usage, RPMsg and remoteproc. Require the existing inference accuracy and repeat-run results at every stage. Stop at a new RPMsg timeout, remoteproc fault, DMA allocation failure or memory layout change. Keep boot and firmware changes separate so the user can restore the previous working entry and noeth image.
